Agentic Architecture & Orchestration

Marcus builds a support agent that keeps talking after it should have finished. He added a max-iteration cap and started parsing the assistant text for done. That is the stall — and it is not a model problem. It is a stop_reason setup problem, and it is fixable.

The one move: While stop_reason is tool_use, run the tool and send the result back. When it's end_turn, stop. Subagents get a clean room — you pass what they need.

Procedure

  1. Send request (tools + messages)
  2. Inspect stop_reason
  3. If tool_use → execute tools
  4. Append tool_result (matched ids)
  5. Repeat until non-tool_use

Teach

The agentic loop (one move)

Send a request with tools. If stop_reason is tool_use, execute those tools, append tool_result blocks (and only those) to history, call again. If stop_reason is end_turn (or max_tokens, refusal, etc.), stop the tool loop. Do not parse natural language for done.

Hub-and-spoke multi-agent

The coordinator holds the plan. Subagents run in isolated context — they do not inherit the parent's chat. Pass findings explicitly in the spawn prompt. Route communication through the coordinator for observability.

Agent tool (formerly Task)

Spawning uses the Agent tool (Task remains an alias in some SDK surfaces). allowed tools must include Agent/Task. Parallel spawn = multiple Agent calls in one response.

Hooks beat prompts for hard rules

Prompt instructions have a non-zero failure rate when money or identity is on the line. PreToolUse can block a refund above threshold. PostToolUse can normalize timestamps before the model sees them. Soft guidance stays in CLAUDE.md; hard guarantees use hooks.

stop_reason is the control plane

Official tool-use docs: after each model response, branch on stop_reason. tool_use means execute tools and continue; end_turn (and other non-tool stops) ends the tool loop. Append tool_result blocks with matching tool_use_id — do not invent completion from prose.

Hooks for deterministic policy

Agent SDK / Claude Code hooks (PreToolUse, PostToolUse) intercept calls and results. Use them for refund ceilings, PII scrubbing, and timestamp normalization. Soft guidance lives in prompts; hard guarantees live in code.

Tool Design & MCP Integration

Maya has eighteen tools and the agent keeps calling the wrong one. She rewrote the system prompt three times. The fix is smaller: four tools with sharp descriptions, not eighteen with one-liners.

The one move: Tool descriptions are how Claude picks the tool. Write them like a careful colleague brief. MCP is USB-C for tools: tools the model calls, resources the app feeds, prompts the user invokes.

Procedure

  1. Design clear tool boundaries
  2. Write rich descriptions
  3. Set tool_choice for the turn
  4. Handle tool_result / is_error
  5. Wire MCP servers by scope

Teach

Descriptions over clever schemas

Say what the tool does, when to use it, when not to, inputs, outputs, and edge cases — three to four sentences minimum. Rename overlapping tools. Split generic analyze_document into purpose-specific tools.

tool_choice modes

auto: model may answer in text. any: must call some tool. forced name: must call that tool first. none: no tools. Forced any/tool prefills so there is no natural language before the call.

Structured errors

Return is_error with category (transient / validation / permission / business), isRetryable, and a clear description. Generic Operation failed wastes retries.

MCP scopes and .mcp.json

Project .mcp.json is shared team tooling with env expansion. User ~/.claude.json is personal. Prefer HTTP for remote servers; stdio for local. Resources expose catalogs so agents stop exploratory fishing.

Descriptions drive selection

Define-tools guidance: clear names + rich descriptions are how the model chooses among tools. Overlapping one-liners cause systematic misroutes. tool_choice auto|any|tool controls whether a tool call is optional, required, or forced to a name.

MCP as the integration bus

MCP separates host, client, and server. Project .mcp.json is team-shared; user config is personal. Prefer ${ENV} expansion for secrets. Structured errors (isError + category + retryability) beat opaque failure strings.

Claude Code Configuration & Workflows

Sam joins the repo and none of the coding standards fire. They lived in the previous developer's ~/.claude/CLAUDE.md. That is not a people problem. It is a hierarchy problem.

The one move: CLAUDE.md is the room that remembers. Put team standards in the project file, personal habits in the user file, and path-specific rules in .claude/rules/ so they only load when needed.

Procedure

  1. Place standards at correct hierarchy level
  2. Split topic rules into .claude/rules/
  3. Add path globs where needed
  4. Create skills for on-demand workflows
  5. Choose plan mode vs direct by complexity

Teach

CLAUDE.md hierarchy

User (~/.claude/CLAUDE.md) is personal and not shared. Project (.claude/CLAUDE.md or root CLAUDE.md) is team and versioned. Directory-level files scope further. Use @import and .claude/rules/ for modular rules.

Path-specific rules

YAML frontmatter paths globs load rules only when matching files are edited — better token economy than dumping everything into one CLAUDE.md. Prefer globs for **/*.test.tsx over directory-only files when tests are spread out.

Skills vs always-on memory

Skills in .claude/skills/ are on-demand workflows with frontmatter (context: fork, allowed-tools, argument-hint). CLAUDE.md is always-loaded standards. Use context: fork so verbose analysis does not pollute the main session.

Plan mode vs direct execution

Plan mode for multi-file architectural decisions. Direct execution for a single well-scoped change. Do not plan a one-line validation fix.

Memory hierarchy

CLAUDE.md at project root is the shared brain. User ~/.claude/CLAUDE.md is personal. Path-scoped rules under .claude/rules/ activate by glob. Slash commands live in .claude/commands/ when they must ship with the repo.

Skills, plan mode, isolation

Skills package repeatable workflows; context:fork keeps exploratory noise out of the main thread. Plan mode for multi-file architectural work; direct execution for one clear, local change.

Prompt Engineering & Structured Output

Linda's review bot flooded the team with style nits. Devs muted every category — including the security ones that worked. Trust is global. Noise in one place taxes everything.

The one move: Vague be conservative does not cut false positives. Explicit categories do. tool_use with a schema kills bad JSON. Independent review beats self-review because the generator keeps its own justifications.

Procedure

  1. Write decidable criteria + severity examples
  2. Add 2–4 few-shot on ambiguous cases
  3. Force schema via tool_use + tool_choice
  4. Validate + retry with error feedback
  5. Review in independent multi-pass architecture

Teach

Explicit criteria, not confidence dials

Report bugs and security issues; skip style and local patterns. Attach severity examples. Temporarily disable noisy categories until precision recovers.

Few-shot when instructions still drift

Two to four targeted examples on ambiguous cases. Show the reasoning, not only the input-output pair. Include format examples and varied document structures for extraction.

Structured output via tool_use

JSON schema via tool_use eliminates syntax errors. It does not fix semantic errors (sums that do not add up). Nullable fields prevent fabrication of missing data. Enums need unclear and other escape hatches.

Batch API and review architecture

Batch is 50 percent cheaper, up to about 24 hours, no latency SLA, no multi-turn tool loops. Keep pre-merge checks synchronous. Review in independent instances; large PRs get per-file passes plus a cross-file integration pass.

Criteria over vibes

Claude 4 prompt guidance: replace 'be careful / high confidence' with operational categories and few-shot boundary examples. Structured outputs (JSON schema / forced tool) make format failures machine-checkable.

Schema mirrors reality

Required fields that are often absent force hallucination. Optional/nullable fields + validation retries for format errors only. Missing source data needs a different remedy — fetch, null, or human — not more retries.

D5 · 15% of exam

Context Management & Reliability

A forty-turn refund chat misquotes the amount after progressive summarization. The agent is not being careless. The facts fell out of the summary. Put them on a shelf the summary cannot throw away.

The one move: Exact numbers die in vague summaries. Keep transactional facts in a case-facts block. Escalate on explicit request, policy gaps, and no progress — not on sentiment.

Procedure

  1. Extract case-facts each turn
  2. Trim tool results at ingestion
  3. Escalate by explicit policy only
  4. Propagate structured errors with partials
  5. Preserve claim-source maps in synthesis

Teach

Preserve critical facts

Extract amounts, dates, order IDs, statuses into a persistent case-facts block outside summarized history. Still pass full history for coherence. Trim tool outputs at ingestion — not after the window is already full.

Lost-in-the-middle

Lead with key findings. Use section headers. Require metadata on subagent outputs so synthesis stays accurate.

Escalation policy

Legitimate triggers: customer asks for a human, policy exception/gap, inability to progress. Explicit demand escalates immediately. Frustration on a solvable issue: acknowledge and offer to resolve; escalate if they reiterate. Multiple identity matches → ask for more identifiers, never pick heuristically.

Error propagation and provenance

Propagate failure type, attempted query, partials, alternatives. No silent empty-as-success. Keep claim-source mappings through synthesis. Annotate conflicts; do not pick one number arbitrarily.

Protect the facts that compress poorly

Long sessions and progressive summarization destroy exact amounts, dates, and IDs. Keep a structured case-facts block outside summarized history. Watch lost-in-the-middle on aggregated inputs.

Reliability is protocol, not hope

Escalation needs explicit criteria and examples. Identity ambiguity requires clarification, not heuristics. Subagent failures return typed payloads. Local retry for transient errors; propagate only unresolvables with partial results.

Drill

Q1 · analysis

After progressive summarization, the agent misquotes the refund amount and promised dates - what got lost, and what structure prevents it?

summaries condensed exact numbers, dates, and customer-stated expectations into vague prose · extract transactional facts (amounts, dates, order numbers, statuses) into a persistent case-facts block · the block rides in every prompt outside the summarized history, immune to compression

Q2 · analysis

Findings from the middle of a long aggregated input keep getting omitted - what is the effect called, what are the two structural mitigations, and what must subagent outputs carry for synthesis to stay accurate?

the lost-in-the-middle effect: beginning and end process reliably, middles get dropped · mitigate: key-findings summary at the beginning, detailed results organized with explicit section headers · subagent outputs must include metadata (dates, source locations, methodological context) so downstream synthesis stays accurate

Q3 · analysis

First-contact resolution is far below target: the agent escalates straightforward damage claims yet attempts policy-exception cases alone - what fix addresses the root cause, and why do confidence thresholds, trained classifiers, and sentiment routing all miss it?

root cause: unclear decision boundaries - add explicit escalation criteria with few-shot escalate-vs-resolve examples to the system prompt · self-reported confidence is poorly calibrated (the agent is already wrongly confident); classifiers are over-engineering before prompt optimization is tried · sentiment tracks emotion, not case complexity - a different variable entirely

Q4 · application

get_customer returns three plausible matches - what must the agent do, and why is picking the best-looking match an anti-pattern?

ask the customer for additional identifiers to disambiguate · heuristic selection risks acting on the wrong account - misdirected refunds and privacy exposure · clarification is the required response to identity ambiguity

Q5 · application

A web-search subagent times out mid-research - what exactly should it return to the coordinator, and what recovery option does each element unlock?

failure type (what happened) -> retry-vs-abandon; attempted query -> retry with modification · partial results -> proceed with what exists; potential alternatives -> redirect strategy · the payload is designed backward from the coordinator's decision space

Q6 · analysis

What are the two opposite error-propagation anti-patterns, and what is the disciplined middle path between them, including who retries what?

anti-pattern 1: returning empty results marked successful - suppression prevents any recovery and corrupts outputs · anti-pattern 2: propagating the exception to kill the entire workflow when recovery could succeed · middle: local recovery for transient failures; propagate only unresolvables, with what was attempted and partial results

Q7 · analysis

An hour into exploration, the agent starts describing 'typical repository patterns' instead of the specific classes it actually found earlier - what is happening and what two immediate mechanisms respond?

context degradation: the specifics have effectively fallen out of usable context · reference the scratchpad of recorded findings to re-ground answers · /compact to reduce context consumed by verbose discovery output

Q8 · application

Design crash recovery for a long multi-agent exploration - what does each agent export, what does the coordinator load on resume, and where does recovered state go?

each agent exports structured state to a known location as it works · on resume the coordinator loads a manifest of that state · recovered state is injected into agent prompts so work resumes rather than restarts
